UCC Intelligence Platform Migration Handover

1. Project Context

This work concerns the United Ceres College (UCC) Intelligence Platform for EduTrust Criteria 1 to 7.

The platform currently uses:

ERPNext / Frappe Server Scripts for backend analytics

A Custom HTML Block for frontend rendering

JavaScript for dashboard behaviour, API calls, charts, filters, diagnostics and exports

CSS for dashboard styling

Separate Python Server Scripts for Criteria 1 to 7

The user only has frontend and ERPNext Server Script access. A custom Frappe app or shared Python module is therefore not practical at this stage.

2. Core Architecture Decision

The final agreed approach is:

Keep seven separate Python Server Scripts

Do not create a new custom app

Do not create a separate shared Python file

Standardise all seven Server Scripts to one common structure

Keep only criterion-specific policies, sources, metrics, questions and requirements different

Keep the existing API method names:

ucc_analytics_criterion_1

ucc_analytics_criterion_2

ucc_analytics_criterion_3

ucc_analytics_criterion_4

ucc_analytics_criterion_5

ucc_analytics_criterion_6

9. Criterion 4 Issue

Criterion 4 originally still queried:

"child_doctype": "Course Adjustment Request Form",
"child_table_field": "custom_course_adjustment"

This caused:

Course Adjustment Request Form is not a valid parent DocType

Affected areas included:

Transfer

Deferment

Withdrawal

Refund

Late admission

The correct treatment was to remove those invalid child-table queries and mark affected metrics as unsupported until a valid replacement structure is confirmed in Student Log or another approved DocType.

Criterion 4 should not return false zeroes for these controls.

13. Cross-Criterion Python Audit

The seven scripts originally had different structures.

Approximate structural groups:

Criteria 1 and 2 used a similar older engine

Criteria 6 and 7 used a similar newer policy-aligned engine

Criteria 3, 4 and 5 each had specialised implementations

Main cross-file issues:

Different payload parsing

Different action names

Different response properties

Different status vocabularies

Different error handling

Different truncation logic

Different filter handling

Different question schemas

Different metric schemas

Some failed queries returned empty lists

Some counts used limited get_list calls

Some scripts used different meanings for source count

Criterion 3 used question_catalogue

Criterion 2 did not originally expose requirement and question registries

Decision:

Keep seven separate Server Scripts, but make the repeated engine code identical.

14. Final Standardisation of Criteria 1 to 7

All seven Python Server Scripts were processed as separate replacement scripts.

Standardised items:

Protected malformed JSON parsing

Filter dictionary validation

Shared action set

Shared response contract

Shared status vocabulary

Shared question-level drill-down metadata

Query errors separated from genuine zeroes

Truncation detection using row_limit + 1

Criterion 3 backward-compatible alias

Criterion 4 obsolete child DocType removal

The final package created was:

UCC_Criteria_1_to_7_Standardised.zip

The package included seven replacement Python Server Scripts plus deployment notes.

16. Important Testing Limitations

The generated scripts were syntax-checked and mock-tested, but they were not executed against the live UCC ERPNext database.

Live testing is still required for:

Actual installed DocTypes

Actual field names

Child-table field names

User permissions

Database values

Workflow states

Frontend response compatibility

Drill-down results

Real source counts

Performance under large datasets

Where the source or field is not confirmed, the script should report unsupported or unavailable rather than show zero.

18. Key Principle

The platform should clearly distinguish:

Record exists

Data is available

Field is complete

Status is completed

Requirement is complied with

Approval exists

Action is implemented

Effectiveness is verified

PDCA loop is closed

These are not equivalent and must not be presented as equivalent in the dashboard.
